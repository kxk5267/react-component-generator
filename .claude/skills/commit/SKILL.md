# commit

변경사항을 분석해 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다.

## 절차

### 1. 변경사항 분석
다음 명령을 병렬로 실행한다.
- `git status` — 변경/미추적 파일 확인
- `git diff` — unstaged 변경 내용
- `git diff --staged` — staged 변경 내용
- `git log --oneline -10` — 기존 커밋 스타일 확인 (커밋이 없으면 생략)

diff를 실제로 읽고 각 변경의 의도를 파악한다. 파일 이름만 보고 판단하지 않는다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 가진다. (기능 추가, 버그 수정, 리팩터링, 설정 변경은 분리)
- 서로 무관한 변경이 섞여 있으면 여러 커밋으로 나눈다.
- 각 커밋에 포함할 파일을 명시한다. 한 파일에 여러 목적의 변경이 있으면 `git add -p` 대신 사용자에게 분리 여부를 묻는다.
- `.env`, 키/토큰, 인증 정보, 대용량 바이너리, `node_modules` 등은 커밋 대상에서 제외하고 사용자에게 알린다.

### 3. 커밋 메시지 작성
형식: `<type>: <한국어 요약>`

| type | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드, 설정, 의존성, 문서 등 기타 |

규칙:
- 요약은 50자 내외, 마침표 없이, "~추가", "~수정", "~개선"처럼 명사형/간결체로 쓴다.
- "무엇을"보다 "왜/무엇이 달라지는가"가 드러나게 쓴다.
- 보충 설명이 필요하면 빈 줄 후 본문에 짧게 적는다.
- 기존 로그에 다른 규칙이 있으면 그것을 우선한다.

### 4. 승인 (기본: 생략)
기본값은 승인 없이 바로 5단계로 진행하는 것이다. 모호한 경우(한 파일에 여러 목적이 섞임 등)도 묻지 않고 가장 합리적으로 판단해 처리하며, 민감 파일은 묻지 않고 커밋에서 제외한 뒤 결과 보고에 명시한다.

사용자가 "확인 후 커밋", "먼저 보여줘" 등 사전 확인을 명시적으로 요청한 경우에만 아래 형식으로 계획을 보여주고 승인을 받는다.

```
커밋 1: feat: 컴포넌트 생성 API 엔드포인트 추가
  - server/routes/generate.ts
  - server/index.ts
커밋 2: chore: eslint 설정 추가
  - eslint.config.js
```

### 5. 커밋 실행
단위마다 순서대로 실행한다.
- 해당 파일만 `git add <파일...>`로 명시적으로 스테이징한다. (`git add -A`, `git add .` 금지)
- 커밋은 HEREDOC으로 메시지를 전달한다.
- 모든 커밋 후 `git status`와 `git log --oneline`으로 결과를 확인해, 만든 커밋 목록(메시지·파일)을 사용자에게 보고한다.

## 금지 사항
- `git push`, `--amend`, `--no-verify`, `reset --hard` 등은 명시적으로 요청받지 않으면 하지 않는다.
- pre-commit 훅이 실패하면 우회하지 말고 원인을 수정한 뒤 새 커밋을 만든다.
- 커밋할 변경사항이 없으면 그렇다고 알리고 끝낸다.
