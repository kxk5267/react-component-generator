# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 사이클 순서를 바꾸거나 단계를 건너뛰지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (엔드포인트, 핸들러, 외부 호출 래퍼)
- **유틸 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR

### 1. RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 테스트를 고쳐서 올바른 이유로 실패시킨다.

### 2. GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 분기, 옵션, 확장 포인트를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### 3. REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경 후마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 요구사항이 끝날 때까지 반복한다.

## 삭제 강제

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 기억해 두고 다시 치기 모두 포함한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 자주 조용히 깨진다. 테스트는 30초면 쓴다. 단순하면 오히려 비용이 거의 없다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현을 베껴 쓰게 되어 **항상 통과**한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD는 **시간을 아끼는 경로**다. |
| "삭제하면 낭비다" | 이미 쓴 코드는 매몰 비용이다. 검증 안 된 코드를 유지하는 쪽이 더 큰 낭비다. 삭제 후 다시 쓰면 보통 더 짧아진다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 적용 대상이면 프로토타입도 예외 없다. 버릴 코드라면 애초에 커밋하지 않는다. |
